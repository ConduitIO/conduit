# Conduit v0.22.0 (draft, not yet released)

This file collects the v0.22.0 notes as changes land. The entries below cover default source batching, the
built-in file and Postgres connector bumps (Postgres v0.21.0 and v0.21.1), the processor SDK bump and the
`conduit-commons` v0.13.1 bump; other v0.22 changes add their own sections.

## Upgrade notes: behavior change

A source that sets no `sdk.batch.*` now reads in batches of up to 100 after you upgrade. No config, state or
protocol format changes and no migration is needed. Opt out per pipeline by setting both settings to 0 (see
"Opting out" below); latency panels, crash-replay and memory behave differently (see "What changes on a dashboard").

`conduit migrate kafka-connect` now translates a Debezium Postgres `table.include.list` exactly. A list of tables in
one schema becomes bare names in `tables` plus `search_path=<schema>` in the source `url`; before, it emitted
schema-qualified names (`inventory.orders`) that the Postgres source refuses at start. A list spanning several schemas,
mixed-case names, system schemas and regular expressions are reported as blocking with a fix. A Debezium Postgres
connector with no `table.include.list` (Debezium captures every non-system schema) is now blocking too: list the tables
explicitly, one connector per schema. Before, the output used `tables: '*'`, which reads only some tables (#3350).

`conduit migrate kafka-connect` now reports, for a Debezium Postgres connector, that Kafka Connect's converters write
a column's schema default, when it has one, in place of NULL, and that Conduit's Postgres source writes the NULL. The
report carries a non-blocking `kc.default_differs` note for each key or value converter that may substitute the
default: a JsonConverter without `replace.null.with.default=false` (Kafka Connect 3.5 and later), a Confluent Avro,
Protobuf or JSON Schema converter without `ignore.default.for.nullables=true`, or any other converter, which the note
leaves to its documentation. Nothing changes in the translation. Consumers that relied on the default must handle
null. Transforms in the chain have their own `replace.null.with.default` setting (Kafka Connect 3.9 and later).

A processor that removes a field from `.Payload.After` only, such as `field.exclude .Payload.After.x` or a
`custom.javascript` that deletes `After.x`, now fails every update that carries a `Before` image on a
schema-attached record (Postgres with `REPLICA IDENTITY FULL`), with `ErrFieldNotInSchema`. With the default
dead-letter queue settings the pipeline stops at the first such record. Before you upgrade, exclude the field
from both parts, for example `.Payload.Before.x,.Payload.After.x` in the same `field.exclude`. See
[the runbook](../operations/field-not-in-schema.md) and "Processor SDK v0.10.0" below.

An Avro decimal that does not fit its schema exactly now fails the record instead of being written truncated. The
common case is `avro.encode` with `schema.strategy: autoRegister`, whose inferred schema is `decimal(31,10)`, fed a
value with more than 10 fractional digits; a negative value with a fraction under a scale-0 decimal is another. The
record goes to the DLQ or the pipeline degrades or keeps recovering, per its dead-letter settings. See
"`conduit-commons` v0.13.1" below and [the runbook](../operations/avro-decimal-not-representable.md).

## `conduit-commons` v0.13.1: Avro decimals that do not fit are refused

Conduit now builds with `conduit-commons` v0.13.1.

- **A decimal that does not fit its schema fails the record.** Before, Avro encoding wrote a `*big.Rat` with more
  fractional digits than the schema's scale truncated, with no error: `1.123456789012` against `decimal(31,10)`
  became `1.1234567890`, `-1.5` against `decimal(5,0)` became `-2`, and `1/3` was cut at the scale. Now the record
  fails, naming the field and the precision and scale the value needs; the value is not in the message. This
  applies to every Avro encode in the process: `avro.encode` with any strategy, and the schema handling of built-in
  connectors and processors. It most often hits `avro.encode` with `autoRegister`, which infers `decimal(31,10)`
  for every decimal whatever the source column is. Standalone plugins encode with their own `conduit-commons` and
  change only when rebuilt on v0.13.1.
  - `avro.encode` with `autoRegister` or `preRegistered` fails with the new code
    `processor.avro_encode.decimal_not_representable`; with `fromRecord` it is `processor.avro_encode.schema_mismatch`
    as before.
  - The record goes to the DLQ, or the pipeline degrades or keeps recovering, per its dead-letter settings. It is
    never acknowledged without being written.
  - Fixes: `schema.strategy: fromRecord`, which encodes with the source's exact decimal type; a pre-registered
    schema with enough scale; or rounding the value on purpose before `avro.encode`. There is no setting to restore
    the truncation.
- **Record data stays out of error messages.** Some Avro, Protobuf and record metadata errors quoted the value they
  failed on; they now name its type and field instead. Only the message text changes.

## Processor SDK v0.10.0: schema-attached updates and the extend strategy

The built-in processors are rebuilt on `conduit-processor-sdk` v0.10.0. It changes how a processor that
reshapes the payload of a schema-attached record (Avro, for example Postgres CDC with a schema registry)
re-encodes the result.

- **Nullable columns that flip to or from NULL no longer fail updates.** On an update where a nullable column
  went from a value to NULL (Postgres CDC with `REPLICA IDENTITY FULL`), a built-in processor that reshaped the
  payload, such as `field.exclude`, failed the record with `unknown union type`. The encoder now builds the
  schema from both `before` and `after`, so these records pass. Shapes that already encoded correctly register
  the same schema text as before. Nested values that flip to NULL still fail the record (SDK issue #196).
- **A processor that removes a field from `after` only now fails the record.** Before, a field present in
  `before` and removed from `after` (for example `field.exclude` on `.Payload.After.x` alone, or a
  `custom.javascript` that deletes `After.x`) was silently missing from `before` in the output. Now the
  record fails with `ErrFieldNotInSchema`, naming the field. To fix a
  pipeline, exclude the field from both parts: `.Payload.Before.x,.Payload.After.x`. The `Before` reference
  also works on creates and snapshots now. `sdk.schema.encode.payload.strategy: extend` does not help here; it
  rejects the same shape. There is no switch to restore the old behavior.
- **Reading or deleting a reference under a missing parent no longer creates `{}`.** A delete record keeps a nil
  `after` instead of coming out with `after: {}`. `Set` and rename still create missing parents.
- **New opt-in parameters on every processor:** `sdk.schema.encode.payload.strategy` and
  `sdk.schema.encode.key.strategy`, each `infer` (default, unchanged) or `extend`. `extend` keeps the carried
  type of every field still present, adds new top-level fields as nullable with a null default, and fails the
  record if a value does not fit its carried type. Nothing changes unless you set it.

Standalone (WASM) processors need a rebuild on SDK v0.10.0 to pick up the changes. The SDK now requires Go
1.26.11, which Conduit already builds with.

## Sources batch by default

Before this release a source that left `sdk.batch.*` unset read one record at a time, and on arch-v2 every
record paid a full round trip (read, write, wait for the destination ack, ack the source). Since
`conduit-connector-sdk` v0.18, `sdk.batch.size` defaults to `100` and `sdk.batch.delay` to `0`. That
combination is **adaptive drain**: the SDK waits for the first record, takes whatever the connector has
already read ahead (up to 100) and returns, with no timer. A busy source delivers batches of up to 100; a
sparse source delivers one record with no added wait.

The built-in connectors are rebuilt on the new SDK in this release, so the default reaches your pipelines
when you upgrade. You do not need to change a pipeline config.

| Connector (source) | Version | Default now |
| --- | --- | --- |
| generator | v0.11.0 | 100 / 0 (batched) |
| file | v0.13.0 | 100 / 0 (batched) |
| kafka | v0.17.0 | 100 / 0 (batched) |
| postgres | v0.21.1 | 0 / 0 (unchanged: CDC keeps its internal batch of 1000, snapshots keep `FETCH 50000`) |
| s3 | v0.13.0 | 0 / 0 (unchanged: each record holds a whole object, and source batches have no byte limit yet) |
| log | v0.9.0 | destination only, no source default |

A standalone connector built with an older SDK keeps its old default. It changes only when its author
rebuilds it on SDK v0.18 or later.

This release makes no throughput claim for the new default. The benchi runs that would back one are not
committed yet.

### Opting out

Set both `sdk.batch.size: 0` and `sdk.batch.delay: 0` on the source connector. That restores one record per
read, exactly as before. You can also go back by reverting the connector version.

```yaml
connectors:
  - id: my-source
    type: source
    plugin: builtin:kafka
    settings:
      sdk.batch.size: "0"
      sdk.batch.delay: "0"
```

### Settings you already have

Settings you set yourself keep their meaning for now:

- `sdk.batch.size` above 0 with no `sdk.batch.delay` (or `0`) still **waits until the batch is full**, with no
  deadline. The SDK logs a WARN with the code `sdk.batch.drain_semantics_pending`. Two SDK minor releases from
  v0.18, that combination will mean adaptive drain. To keep full batches, set `sdk.batch.delay` above 0 now.
  See [the runbook](../operations/source-batching.md).
- `sdk.batch.delay` above 0 with `sdk.batch.size: 0` now uses a bounded batch size (1000) and logs
  `sdk.batch.size_defaulted`. Before, a `Read`-based connector batched without an upper bound there, and a
  `ReadN` connector such as Postgres failed or did not batch. Set `sdk.batch.size` explicitly.
- A connector whose own default delay is non-zero (MySQL's is 1s, for example) and a pipeline that sets
  `sdk.batch.delay: 0` keep wait-until-full and log `sdk.batch.unbounded_wait`.
- `sdk.batch.size` is now a hard cap, including for connectors that return more records than they were asked
  for. The excess is kept for the next batch, in order.
- If a source returns an error partway through a batch, the records collected before the error are delivered
  first, then the error.

The three codes are registered as Conduit error codes (`sdk.batch.unbounded_wait`,
`sdk.batch.size_defaulted`, `sdk.batch.drain_semantics_pending`, gRPC `InvalidArgument`). Today the SDK reports
them as warnings in the connector's log. If a later SDK turns one into a rejection, Conduit returns the
code, the config path and a suggested fix, with the SDK's message unchanged, from pipeline start and from
config validation.

### What changes on a dashboard

- **Latency panels and alerts move.** `conduit_pipeline_execution_duration_seconds` is measured from the
  record's `opencdc.readAt`, which the SDK stamps when the connector builds the record. It therefore includes
  time spent in the SDK's read-ahead and in a batch waiting for the engine. After the upgrade a record on a
  dense source waits behind up to about 200 others instead of one, so the distribution shifts upward even
  when throughput improves. A sparse source is not affected. We have not measured the size of the shift and do
  not publish a figure; compare your own p99 before and after, and re-baseline alerts.
- **Crash replay window.** After a crash the pipeline replays everything after the last persisted position.
  That window is now bounded in positions: 10,000 (the persister threshold), plus one in-flight batch, plus
  whatever destination batching holds. Records the SDK read ahead but never sent are re-read, not
  duplicated.
- **Memory.** A source holds roughly three batches of records (read-ahead, the batch being collected, and
  one in flight). With large records that scales linearly; set both settings to 0 for a source with very
  large messages. Kafka in particular holds up to about 200 more fetched but unacked records, which a
  consumer-group rebalance or restart redelivers (at-least-once, as before, with a larger window).
- **Graceful stop** drains one batch instead of one record. Records read ahead but not sent are dropped
  unsent and unacked, and replay on the next start.

### Destination write size

At the default, the engine passes a source batch straight to the destination in one write. For a standalone
destination that would exceed `connectors.max-receive-record-size` (4 MiB by default) with large records.
The arch-v2 engine splits such a write by estimated wire size, for destinations and dead-letter queues
(#3296, #3301). The classic engine writes one record at a time and is not affected. A single record larger
than the limit is nacked with `pipeline.record_exceeds_max_receive_size`.

## Postgres: `snapshot.fetchSize` now works

`conduit-connector-postgres` v0.19.0 reads the documented `snapshot.fetchSize` parameter, which was parsed and
never used. It sets the snapshot cursor page size (default 50000), and a value of 0 or less is rejected at
startup. `sdk.batch.size` no longer sets the snapshot page size. The default is what you got before with
`sdk.batch.size` unset, so default pipelines see no change. If you set `sdk.batch.size` on a Postgres source
only to tune snapshot paging, move that value to `snapshot.fetchSize`.

## Other changes in this area

- The state persister counts positions, not calls. Source acks pass the number of positions in the acked
  batch and the threshold is crossed with `>=`. Before, with batches that do not divide 10,000 evenly (37,
  100, 1000), a count-equals check could be stepped over and the one-second timer became the only trigger.
- `conduit-connector-protocol` moves to v0.12.0 through the SDK. The change is additive: destinations may
  declare `ordered_acks`, and the Go SDK now acks destination records in receive order. Older engines and
  plugins ignore the field.

## Arch-v2: a destination write that fails while the source is idle fails the pipeline

On `--preview.pipeline-arch-v2`, a batching destination that is the only destination of its pipeline writes
on a background flusher. When that write failed after the source had gone quiet, the pipeline kept reporting
**running** and wrote nothing until another record arrived or it was stopped. The failure now ends the run
right away: the pipeline goes to recovering, or to degraded if the error is fatal (a failed DLQ write, an
exceeded nack threshold). No records were at risk before or after: the failed flush and everything behind it
were never acknowledged and are delivered again. See
[the runbook](../operations/archv2-destination-batching.md#a-batched-write-fails-while-the-source-is-idle).

## Arch-v2: `sdk.batch.delay` bounds how long a destination's partial batch waits

On `--preview.pipeline-arch-v2`, a destination that sets `sdk.batch.delay` now has its partial batch written
at the latest that delay after the batch's first record, even when no further record arrives. Before, the
delay was checked only when the next record arrived, so on a source that went quiet the last records stayed
unwritten and unacknowledged until more records came or the pipeline was stopped (#3231; the v0.21 smoke run
held the last 5,088 of 300,000 records this way). No records were at risk: nothing was acknowledged before it
was written. The default engine is unchanged; its connector SDK already had this timer.

- On a pipeline with several destinations, a record one destination nacks while another batches with a delay
  now reaches the DLQ (or, with the default DLQ, fails the pipeline) within that delay on a quiet source.
- A destination that batches by `sdk.batch.size` alone still has no time bound, as in the connector SDK. The
  start logs `pipeline.archv2_destination_batch_unbounded_wait` for it; set `sdk.batch.delay` to bound the wait.
- New metrics: `conduit_funnel_destination_flushes_total` (by trigger, including `deadline_timer`) and
  `conduit_funnel_destination_flush_linger_seconds`. See
  [the runbook](../operations/archv2-destination-batching.md#a-partial-batch-waits-longer-than-sdkbatchdelay).

## Arch-v2: the engine owns destination batching, including connector defaults

On `--preview.pipeline-arch-v2`, the engine now batches a destination with its effective `sdk.batch.size` and
`sdk.batch.delay`: the value in the pipeline config, else the default the connector declares. It hands the
connector `0` for each of those keys that would otherwise turn the connector's own batcher on (#3321). No
config, state or protocol format changes. The default engine is unchanged.

- **S3 destinations are batched without any setting.** `conduit-connector-s3` declares 1000 records / 1 s. Before,
  arch-v2 did not batch it unless the pipeline set `sdk.batch.*`, the connector batched internally and held
  every acknowledgement for up to a second, and a pipeline whose source reads one record at a time delivered
  about one record per second (the v0.21 smoke run: 2,690 records in 45 minutes). Now the engine batches it at
  1000 / 1 s. **Object layout changes:** such a pipeline writes one object per batch (up to 1000 records, or what
  arrived within a second), not one object per record, the same layout the default engine produces.
- **No more double batching.** When the pipeline set `sdk.batch.*` on such a destination, the engine removed the
  keys before configuring the connector, which brought the connector's own default back, so any engine flush
  smaller than 1000 records waited another second inside the connector. The connector now gets `0`.
- **Dead-letter queue.** A dead-letter queue with `sdk.batch.delay` above 0 is now refused at start, and by a live
  apply, with `pipeline.archv2_destination_batching_unsupported`, as `sdk.batch.size` above 1 already was: the SDK
  batches on a delay alone, so each nacked record waited for the delay. **An arch-v2 pipeline that sets it no
  longer starts;** remove the setting. A dead-letter queue that batches only by its connector's default (S3) is
  handed `0` and writes each nacked record at once.
- **`sdk.batch.*` must be a literal on arch-v2.** A destination or dead-letter-queue `sdk.batch.size` or
  `sdk.batch.delay` that contains `$` (an environment reference such as `${S3_BATCH}`) is refused at start, by a
  live apply, and by `pipelines validate` and `doctor`, with `pipeline.archv2_destination_batching_not_literal`.
  The engine decides how to batch from the value as written, and the reference is expanded only for the
  connector, so the connector could batch behind the engine and stall it. **An arch-v2 pipeline that uses a
  reference there no longer starts;** write the value instead. The default engine is unchanged. See
  [the runbook](../operations/archv2-destination-batching.md#arch-v2-refuses-an-environment-reference-in-sdkbatch).
- **The offline arch-v2 check matches the engine.** With `--preview.pipeline-arch-v2`, `pipelines validate`,
  `lint`, `dry-run`, `doctor` and the MCP `arch_v2` check no longer report a destination that sets `sdk.batch.*`,
  so they no longer exit with an error for such a pipeline. They report what start refuses: a dead-letter queue
  with `sdk.batch.size` above 1 or `sdk.batch.delay` above 0, and a non-literal `sdk.batch.*` value.
- A connector that batches inside its plugin without declaring `sdk.batch.*` is not covered; set `sdk.batch.*` in
  the pipeline so the engine batches it.
- New: an INFO log at start, `destination batching taken over from connector defaults`, and the metric
  `conduit_funnel_destination_plugin_batching_neutralised_total`. See
  [the runbook](../operations/archv2-destination-batching.md#a-destination-is-slow-behind-a-1-record-source).

No records were at risk before or after: nothing is acknowledged to the source before the destination
acknowledges it.

## File connector v0.13.0: a killed destination leaves no torn line, and acknowledged records are durable

Built-in `file` moves to v0.13.0. A destination killed while writing (SIGKILL, the OOM killer) could leave the
output ending in part of a record, and the next record was glued to that fragment, corrupting both. An
acknowledged record could also be lost to an operating-system crash or a power loss. Both are fixed.

- **No torn last line after a kill.** The destination records the committed length of the output in
  `<path>.committed`, next to the output. On open it cuts the output back to that length and logs a warning
  with the path, the old and new size and the bytes removed. Those bytes belong to a batch that was never
  acknowledged, so it is delivered again.
- **Acknowledged records survive an operating-system crash or a power loss** on storage that honors fsync. Each
  write fsyncs the output, records the new length, fsyncs `<path>.committed` and only then returns. Opening the
  destination fsyncs the output's directory. A disk write cache without power-loss protection, or a filesystem
  mounted without write barriers, can still lose data the operating system reported as synced.
- **No write after a failed write.** After an I/O error, a full disk or a failed fsync the destination refuses
  further writes until it is opened again, so the next batch cannot land after part of the failed one.
- **Destination batching is on by default.** `sdk.batch.size` defaults to `1000` and `sdk.batch.delay` to `100ms`,
  because every write now pays for two fsyncs. To write each batch the engine passes as it arrives, set **both**
  to `0`. With only one of them at `0` the destination still batches.
  On `--preview.pipeline-arch-v2` the engine applies the connector's `1000` / `100ms` default itself and hands the
  plugin `0`, so no setting is needed there either (see the arch-v2 section above).
- **New option `dirSync.acceptUnsupported`** (default `false`). Some network and FUSE filesystems reject fsync on
  a directory. On those, opening the destination now fails with `FILE_DIR_SYNC_UNSUPPORTED`, because a newly
  created output might not survive a crash. The error names the directory and the fix. The connector README
  explains how to make the entries durable first and what can still be lost once you set the option.
- **New error codes:** `FILE_COMMITTED_LENGTH_MISMATCH`, `FILE_COMMITTED_LENGTH_INVALID`,
  `FILE_OUTPUT_TAIL_UNTERMINATED`, `FILE_DIR_SYNC_UNSUPPORTED`. Each message names the path and the fix.

Upgrade notes:

- No configuration change is needed. An output from v0.12.0 or earlier has no `<path>.committed`. With a `*/json`
  record format (the default `opencdc/json`, or `debezium/json`) the first open cuts a partial last line once,
  with a warning, and records the length from then on. With another record format, such as `template`, a record
  can contain a newline, so an output that does not end with a newline fails to open with
  `FILE_OUTPUT_TAIL_UNTERMINATED`. Inspect the end of the file, remove the partial record and restart.
- **`<path>.committed` is part of the output.** Keep it next to the file, back it up and restore it with the
  file, and do not edit it. Do not let a source's `rotatedPattern` match it.
- **Throughput.** A pipeline that delivered one record per write is now bound by the device's sync latency unless
  it batches. The new defaults batch; if you set the destination's `sdk.batch.size` or `sdk.batch.delay`
  yourself, check them against the note above.
- **A `builtin:file` dead-letter queue on the default engine holds each nacked record for 100ms.** The default
  engine writes one dead-letter record at a time and waits for it, so the new `sdk.batch.delay` default of `100ms`
  slows a pipeline that nacks many records to about ten per second. Under `dead-letter-queue.settings` set
  `sdk.batch.size: "0"` and `sdk.batch.delay: "0"`. On `--preview.pipeline-arch-v2` the engine already hands the
  dead-letter queue `0`, so nothing is needed there. See
  [the runbook](../operations/file-dead-letter-queue-batching.md).
- **Setting only `sdk.batch.delay: 0`** leaves `sdk.batch.size` at `1000`, and a partial batch then waits until it
  is full. Set both.
- **Downgrading after a crash.** v0.12.0 and earlier ignore `<path>.committed` and append without updating it.
  If an older version appends acknowledged records after a crash, upgrading again cuts them off as
  unacknowledged. Delete `<path>.committed` before starting v0.13.0 again after such a downgrade.
- Devices and FIFOs (for example `/dev/stdout`) are written as before, without `<path>.committed` and without
  fsync.

## Postgres connector v0.21.0: Avro schemas match the table

Built-in `postgres` moves to v0.21.0. This is a minor release because registered Avro schemas change.

- **Nullable columns are `["null", T]`.** With the default `logrepl.withAvroSchema: true`, every column used to be
  registered as a plain type, so a `NULL` in any nullable column failed to encode and stopped the source, again
  after every restart. The source now reads nullability from the catalog: a column that is not `NOT NULL` is the
  union `["null", T]` with a default of `null`, as Debezium's Avro converter does. `NOT NULL` columns, primary
  keys included, stay the plain type. `NULL` is delivered as `null` for every type. A `NULL` in a `uuid` column
  used to be an empty string in the snapshot.
- **`json` and `jsonb` are strings.** They were Avro `bytes`. They are now a string named
  `io.debezium.data.Json`, holding the exact text Postgres prints: key order, `1.50` and
  `12345678901234567890` are kept. `json[]` and `jsonb[]` elements are exact text too.
- **Invalid UTF-8 json is delivered as base64.** Only a source database whose `server_encoding` is not `UTF8`
  (in practice `SQL_ASCII`) can hold such text. New option `json.invalidUTF8`: `base64` (default) writes the
  standard padded base64 of the exact bytes and lists the column in the record metadata
  `postgres.json.raw_bytes` (`postgres.json.raw_bytes.before` for `payload.before`); `halt` stops the source with
  `postgres.source.json_not_utf8`. No byte is replaced or dropped. A consumer that ignores the metadata reads the
  base64 text as if it were the JSON value, so decode the listed columns, or use `halt` for pipelines whose
  consumers cannot be updated.
- **The destination decodes the listed columns** and writes the bytes instead of the base64 text. It fails the
  write with `postgres.destination.json_raw_bytes_invalid`, storing and acknowledging nothing, when the metadata
  is malformed, a listed column is missing from the record, or a listed value is not strict padded base64. A
  processor that changes, renames or drops a listed column must update or remove the metadata.
- **Schema registry compatibility.** `T` to `["null", T]` is `BACKWARD` compatible and not `FORWARD` or `FULL`
  compatible. The built-in registry does no compatibility check, and subjects Conduit creates in a Confluent
  registry get `NONE`, so nothing is rejected there. A subject created outside Conduit keeps the registry's
  level: `BACKWARD` (the default) accepts the new version, `FORWARD` or `FULL` rejects it, and the source stops
  with nothing acknowledged. Relax the subject to `BACKWARD` for the upgrade, or upgrade the consumers first.
  Consumers must handle `null` for nullable fields, and processors that type-assert a json field to `[]byte`
  must accept `string`.
- **`evolve` drift policy.** A column type change from `bytea` to `json` or `jsonb` is no longer admitted
  automatically under the `evolve` policy, because the two types are no longer wire compatible.
- An `UPDATE` that leaves a TOASTed column unchanged, with Avro on, now stops the source with
  `postgres.avro.unchanged_toast`. v0.20.0 already stopped the source on such a record (with a `missing required
  field` error); the stop now has an error code. Set `REPLICA IDENTITY FULL` on such
  tables to avoid it.
- New error and warning codes: `postgres.avro.unchanged_toast`, `postgres.avro.toast_identity`,
  `postgres.avro.null_in_not_null_column`, `postgres.source.json_not_utf8`,
  `postgres.source.json_server_encoding`, `postgres.destination.json_raw_bytes_invalid`.

Upgrade notes:

- The upgrade is automatic. Positions, checkpoints and state are not touched. The first record of each table
  with a nullable column registers a new version of its payload subject.
- **Upgrade the destination with the source, or before it.** An older destination writes the base64 text of a
  listed column into a `text` column without an error. Conduit's built-in connector ships source and
  destination at the same version, so only mixed standalone setups are affected.
- Rolling back to v0.20.0 is safe for data. It registers the old shapes again, which a registry that enforces
  `BACKWARD` or `FULL` on the subject rejects, and v0.20.0 stops on the first `NULL` it reads, as before.

## Postgres connector v0.21.1: CDC relations are named by schema and table

Built-in `postgres` then moves to v0.21.1, a patch release for a data-correctness bug
([#424](https://github.com/ConduitIO/conduit-connector-postgres/issues/424)). A publication that already exists
under `logrepl.publicationName` is reused as it is, and a Debezium import can leave it covering more tables than
`tables`. It can then stream a table from another schema with the same name as a configured table. That table
took the configured table's `opencdc.collection` and key column, and with an `id` column in both its rows reached
the destination as the configured table's rows and upserted over them.

- **Configured tables are unchanged.** Each configured table is resolved to its relation OID and schema at start,
  with the same quoting and `search_path` as the snapshot and the publication. A CDC relation that is that table
  keeps the configured name as collection, key column and Avro subject, including after
  `ALTER TABLE ... SET SCHEMA` while the pipeline runs.
- **Other tables are named `<schema>.<table>`.** That is their `opencdc.collection`; with Avro on, their subjects
  are `<schema>.<table>_payload` and `<schema>.<table>_key` (new subjects, version 1). Their key is empty and
  they are not snapshotted. The first change of each such relation logs a warning with
  `postgres.source.unconfigured_table`.
- **Who sees a change.** Pipelines whose publication covers only `tables` (every publication the connector created
  itself) are unaffected, unless DDL renames a configured table while they run (it becomes `<schema>.<new name>` with
  no key; a move keeps its name). A pipeline that reuses a wider publication (hand-made, `FOR ALL TABLES`, `FOR TABLES
  IN SCHEMA`, Debezium import) now receives `<schema>.<table>` for the extra tables. A destination that routes on the
  collection sees a new name, and the Postgres destination with its default template reports
  `postgres.destination.table_not_found` for them. Add those tables to `tables`, or use a publication that covers only
  the configured tables.
- **New stop: `postgres.source.configured_table_ambiguous`.** If a configured table was moved to another schema,
  a new table took its name and both are streamed, the source stops before emitting anything for that change.
  earlier versions delivered both as the configured table. Restart the pipeline: the name is resolved again and the other
  table is named `<schema>.<table>`. The table that holds the name after the restart was never snapshotted, so
  only its later changes are delivered. To get its existing rows, either re-snapshot (delete and recreate the
  source connector so it has no position; every configured table is read again, so the destination must tolerate
  duplicates), or read that table with a separate source connector: `tables` set to it, `snapshotMode: initial`,
  its own `logrepl.slotName` and `logrepl.publicationName`. Keep the separate connector running after its snapshot
  until its CDC has caught up past the snapshot. Until then its snapshot rows race the main pipeline's updates and
  deletes of the same keys in the same destination table, and can regress a value or resurrect a deleted row.
  Then stop it and drop its slot and publication (delete it with `logrepl.autoCleanup` left at `true`).
- **Go 1.26.11.** The connector is built with it, matching the Conduit toolchain.

Positions, checkpoints, acks, ordering and serialized formats are untouched. The upgrade is automatic. Rolling
back is safe for data: records return to the bare table names, which also brings back #424 for pipelines on a
wider publication. Details: the connector README section "Table
Names and `opencdc.collection`".

## `avro.encode`: keep the source's Avro types (`schema.strategy: fromRecord`)

`avro.encode` with `schema.strategy: autoRegister` infers a schema from the decoded values and ignores the
schema the record carries. A Postgres `int4` therefore reaches Kafka as `long`, a `numeric(14,2)` as
`decimal(31,10)` and a `date` as `timestamp-micros`. The values are the same, but a consumer whose reader schema
matches the source (Debezium-shaped consumers, for example) cannot read them.

The new, opt-in `schema.strategy: fromRecord` encodes with the schema the record carries (its
`opencdc.payload.schema.*` or `opencdc.key.schema.*` metadata), leaves out each top-level field a processor removed,
adds a nullable field with a null default for each top-level field the record adds (such as `__op`), and registers
the result under `schema.fromRecord.subject`:

```yaml
- id: avro
  plugin: avro.encode
  settings:
    field: .Payload.After
    schema.strategy: fromRecord
    schema.fromRecord.subject: cdc.public.orders-value
```

- `field` must be `.Key`, `.Payload.After` or `.Payload.Before`.
- A value that does not fit the schema exactly fails the record (DLQ or degraded pipeline, per your DLQ
  settings). Nothing is converted, truncated or filled with a default. New error codes:
  `processor.avro_encode.schema_mismatch`, `processor.avro_encode.schema_unsupported`,
  `processor.avro_encode.registry_unavailable`, `processor.avro_encode.schema_incompatible`.
- A top-level field removed before `avro.encode` (for example with `field.exclude`) is left out of the registered
  schema. A field that is still there keeps its carried type, so a mistyped value still fails.
- An empty key or payload part (nil, or raw data with no bytes, as a delete record's `.Payload.After` often is) is
  not encoded: the record passes through unchanged.
- A record that carries no schema is encoded with an inferred schema, as with `autoRegister`, logged once and
  counted by `conduit_processor_avro_encode_schema_fallback_total`.
- A processor before `avro.encode` that adds or removes fields (for example `field.set`) registers an inferred
  schema for its output by default. Set `sdk.schema.encode.payload.enabled: false` on that processor so the
  record still carries the source schema. Or set `sdk.schema.encode.payload.strategy: extend` on that processor
  (`conduit-processor-sdk` v0.10.0): its middleware then builds the new schema version from the carried schema,
  so the source types are kept and the payload still gets re-encoded. `extend` fails the record if a value does
  not fit its carried type, if a nested record gains or loses a key, or if `payload.before` and `payload.after`
  end up with different top-level fields (on an update, change both parts).
- Opting in changes the schema registered under the output subject. A subject that holds earlier `autoRegister`
  versions can refuse it under the registry's compatibility rule (`decimal(31,10)` to `decimal(14,2)` is not a
  legal promotion), so use a new subject for the switch.

`autoRegister` and `preRegistered` are unchanged in this release. Plan: in v0.23 `autoRegister` warns when it
infers a schema for a record that carries one; in v0.24 it uses the carried schema by default. Design:
`docs/design-documents/20261106-avro-encode-preserve-source-schema.md`.
