# v0.21 certification gaps for the `conduit migrate kafka-connect` targets

Status: draft, 2026-10-12; issue states and versions refreshed 2026-10-14. Roadmap item: v0.21, "Migrate from
Kafka Connect, part 1". Depends on `ConduitIO/conduit#2951` (the catalog inventory that defines "Certified"),
which must merge first.

Every connector that `conduit migrate kafka-connect` emits in v0.21 has to be certified in the same release.
This document lists, per connector, what stands between today's code and that bar, based on reading the code,
the READMEs and CI configuration, and the fixes opened so far. Findings are from code reading unless a test run
is named. Nothing here has been benchmarked.

"Certified" uses the definition in [the catalog inventory](../catalog-inventory.md) (PR #2951): the SDK
acceptance suite and an integration test against the real system, both running in CI; a kill -9 chaos test; a
committed benchi configuration with a recorded run; and user docs covering configuration, delivery semantics and
an example pipeline. This document adds two requirements the registry design already implies: a signed
release (cosign plus SLSA provenance) and a license file.

Sizes: S = under a week, M = one to three weeks, L = more than three weeks, for one engineer who knows the SDK.

## 0. Built-in Postgres source (`ConduitIO/conduit-connector-postgres`)

Why it is in scope. The merged `docs/design-documents/20261012-migrate-kafka-connect.md` (_Connector mapping_)
maps `io.debezium.connector.postgresql.PostgresConnector` to the `builtin:postgres` v0.15.0 source with a
`builtin:kafka` destination, and `io.confluent.connect.jdbc.JdbcSourceConnector` to the `postgres` or `mysql`
source. Both are v0.21 targets, so the built-in Postgres source has to be Certified in v0.21. It is the most
used migrate target, and the only one whose migration promises a resume without re-snapshot.

State on 2026-10-14. Latest release v0.14.4; Conduit `main` pins v0.14.3. v0.15.0, which the migrate doc
names, is not released. The repo has a SIGKILL chaos harness for the source (`test/chaos`,
`docker-compose.chaos.yml`) and integration tests against a Postgres container. It has no SDK acceptance
suite for either the source or the destination: postgres#348 tracks running acceptance suite v2 in CI
(source and destination), #343 the destination's v1 suite. Signing: `publish.yml` with
cosign and SLSA provenance, as for the destination. Benchi configs were not checked in this pass. Lane:
`ConduitIO/conduit#3004`.

### P0: Debezium-compatible output (#3032)

A Debezium Postgres pipeline emitted by `migrate` writes to Kafka for consumers built for Debezium events. With
today's OpenCDC output those consumers break on the first record. The migrate doc translates `topic.prefix`
and the Debezium type and tombstone options only "when the pipeline uses Debezium-compatible output mode", and
marks every option the mode does not support as blocking. So without the mode, every Debezium Postgres
migration to Kafka has a blocking entry, and the theme of the release does not hold for its main path. Status:
design merged (#3033); no implementation merged (#3032, checked 2026-10-14). It is Tier 1 (a public record
format). It ships opt-in, versioned, with a diff harness against real Debezium. Certification for this source
therefore covers the source with the output mode on as well as off.

### Debezium offset import (#3004)

The migrate doc promises "no re-snapshot": Conduit creates its own slot, waits until Debezium's committed
offset is past the new slot's consistent point, then resumes from Debezium's offset. The design is
`conduit-connector-postgres#341` (merged 2026-10-13), the CLI surface is `ConduitIO/conduit#3029` (merged
2026-10-13). No implementation is merged. This is a position change (invariant 2) and needs the lane's own
gates: a versioned position migration with an upgrade test, kill-mid-import and kill-mid-checkpoint SIGKILL
tests, idempotent import, stable error codes for a malformed or mismatched offset, and an end-to-end test with
a real Debezium connector's offsets. Without it `migrate` emits `kc.resume_unavailable` (blocking) for
`snapshot.mode=never`, and every other Debezium migration re-snapshots.

### What acceptance v2 must prove for it

Acceptance suite v2 (`conduit-connector-sdk#397`, lane #3011) is the bar. For this source the driver has to
seed real tables through SQL, including the CDC phase after the snapshot, and the run has to claim, not skip,
the capabilities the migration relies on:

- SRC-03 `crash_resume_no_gap` with the restarts inside the snapshot, at the snapshot-to-CDC boundary and inside
  CDC, against a real replication slot. This is the case that proves resume, which is what the offset import
  builds on. `ExactResume` is not expected: logical replication resumes from the confirmed flush LSN, so the
  claim is a declared `MaxRedelivery` bound, and the suite checks that bound exactly.
- SRC-04 `ordering_per_key` claimed (`Source.OrdersByKey`): per-table, per-key order is what Debezium consumers
  assume (invariant 4).
- SRC-05 `schema_evolution` claimed with `evolve`: a column added mid-stream must reach the record, not be
  dropped (invariant 6).
- SRC-06 `large_record` with values stored out of line (TOAST), which is where #383 lives.
- SRC-07 `graceful_stop_with_unacked` and SRC-08 `context_cancellation`: a stop with unacked records must not
  advance the flush LSN past them (invariants 1 and 7).
- SRC-01, SRC-02 and SRC-09 as for any source.
- The run is postgres#348: suite v2 in CI for the source and the destination (it also tracks the
  `connector.yaml` description that fails Core).
- With Debezium-compatible output on, the same cases pass. The diff harness (#3032) proves the format; the
  suite proves the delivery semantics do not change with it.
- The postgres destination (JDBC sink) needs DST-01 to DST-11, with `Destination.OrdersByKey` claimed and
  idempotence claimed only for keyed upserts. DST-04 `crash_replay_at_least_once` is the case that would have
  caught postgres#342.

The acceptance run does not replace the source's own SIGKILL chaos tests or the offset-import kill tests;
those stay required.

To certify (L): Debezium-compatible output (#3032) and offset import (#3004) implemented and signed off;
fix #344, #383 (via #388 or another design), #326, #376, #377, #391 and #392; decide #312; fix #386, #367
and #402 for the JDBC sink path (#374 is loud and can follow); close #347 on a passing SRC-08; #378 only if
the standalone plugin is certified too;
acceptance suite v2 in CI for source and destination; kill tests for the import and the Kafka-sink path;
re-run the committed benchi configs; release v0.15.0 and bump the built-in.

## 1. MySQL source (`ConduitIO/conduit-connector-mysql`, beta)

Acceptance suite. Not present before `ConduitIO/conduit-connector-mysql#192` (open), which adds it and runs it in
the existing `test` job
against the compose MySQL 8.0.39. The suite only drives sources through `Read`, and this source implements only
`ReadN` and is ack-gated, so the test wraps it in an adapter. `TestSource_Open_ResumeAtPositionCDC` is skipped
because a restart from a CDC position re-snapshotted every table (#158, now fixed by mysql#195, merged
2026-10-14). The PR also fixes a data race in
`NewSource` (shared package-level batch settings) that made the suite flaky.

Parity with Debezium MySQL:

| Debezium option | Status |
| --- | --- |
| `snapshot.mode` | Approximated: `snapshot.enabled` boolean only. No `schema_only`, `when_needed`, `initial_only` |
| `snapshot.fetch.size` | Supported (`snapshot.fetchSize`) |
| Snapshot consistency | Approximated: brief `FLUSH TABLES WITH READ LOCK` to read the binlog position, but rows are not read in one consistent transaction, so CDC replays some changes |
| `table.include.list` / `exclude.list` | Approximated: ordered regex list with `+`/`-`, one database, resolved once at `Open` |
| `column.include` / `exclude` | Missing (use a processor) |
| `database.server.id` | Missing |
| GTID | Missing: positions are binlog file, offset and row index |
| Schema history | Missing: reads live `information_schema`; replay across an ALTER is untested |
| Heartbeat | Missing: position advances only on events from included tables |
| Tombstones | Missing |
| `decimal.handling.mode` | Missing: DECIMAL is always float64, lossy (#191) |
| `time.precision.mode` | Approximated: temporal columns are strings |
| Unsigned integers | Broken above 2^63 (`ConduitIO/conduit-connector-mysql#86`) |
| Incremental / signal snapshot | Missing |
| Binlog position resume | Supported; stable error when the binlog was purged |
| SSL | Unverified: the SQL connection honors the DSN, the binlog stream likely does not |
| MariaDB | Missing |

Delivery semantics. Good: snapshot-to-CDC handoff is ack-gated and tested; CDC start position is taken under
the table lock; positions carry a version envelope; the snapshot ack wait on teardown is bounded.
Problems:

- #158 (fixed by mysql#195, merged 2026-10-14, not released): restart from a CDC position re-snapshotted all
  tables (duplicates scale with table size; resume can lag past binlog retention).
- Cold-start gap: with an empty snapshot or `snapshot.enabled=false`, a crash before the first CDC ack loses
  events between the start position and the restart (design doc lists this as pending SDK #378). Invariant 3.
- Unsafe snapshot (`snapshot.unsafe`, tables without a primary key): position not persisted, and `Teardown`
  hangs mid-snapshot (#190). Invariant 7.
- Composite primary key snapshot fails after the first chunk (#189).
- Every canal error is labeled `ErrCDCStartPositionUnavailable`, which can mislead operators.

Schema handling. Invariant 6 violations, observed in probes against the connector: NULL is emitted as a zero value,
DECIMAL(30,10) comes out as a float64, and BIGINT UNSIGNED above 2^63 is silently corrupted on the snapshot path
(18446744073709551615 came out as 3474867090068222261); the CDC path halts at the encoder instead. Design:
`ConduitIO/conduit#3040`.

Snapshot position defect (`ConduitIO/conduit-connector-mysql#204`; observed in a spike on unmodified code with
`fetchSize=2`, a partial ack and a restart; no in-repo regression test yet): the last-read key is stored in the
position as raw driver bytes and returns as base64 or float64, so
resume loses rows for negative DECIMAL keys, BIGINT keys above 2^53 and BIGINT UNSIGNED keys. This is a data-loss path
(invariant 2 and 3) and needs its own Tier 1 fix; #3040 does not fix legacy mode. Unknown column types halt, which is
acceptable. DDL mid-stream is untested.

Tests. Integration tests against a MySQL container run in CI with `-race`, including crash, handoff-gate,
snapshot and CDC tests. No benchi config, no upgrade test, no SIGKILL chaos suite beyond the existing crash
test.

Signing and license. Apache-2.0 `LICENSE` exists (added 2026-10-08, `ConduitIO/conduit-connector-mysql#185`; the
inventory's
"none-detected" is stale). `release.yml` is plain GoReleaser: no cosign, no SLSA, no `publish.yml`.

To certify (L):

- Release the #158 fix (mysql#195); fix #189, #190.
- Design doc for DECIMAL, NULL and unsigned semantics (a payload contract change), then fix #191 and #86.
- TLS for the binlog stream.
- Decide GTID and heartbeat (see decisions).
- SIGKILL chaos tests mid-snapshot and mid-CDC; position upgrade test.
- Benchi config with a recorded run, copied from the existing `streaming-benchmarks` MySQL configs.
- User docs with delivery semantics and an example pipeline.
- Signed publish workflow (copy from `postgres`), registry entry.
- Remove the acceptance skip.

Acceptance. The `mysql` destination passes the suite in `ConduitIO/conduit-connector-mysql#192`. `postgres` has no
acceptance test;
a local probe failed `TestDestination_Write_Success` because `Write` mutates the caller's payload
(postgres#343). The probe also reported goroutine leaks, which may be an artifact of the probe's own connection
(not verified).

Ack correctness (both Tier 1):

- `mysql`: after a rollback, `Write` returns earlier batches as written, so the SDK acks records that were
  never stored (#187). `DELETE` on a table with no primary key deletes every row (#188). Both are fixed in
  `ConduitIO/conduit-connector-mysql#193`. Still open: upsert columns come from the first record in a batch; an update
that changes the
  key leaves the old row; the primary-key cache goes stale if a key is added later.
- `postgres`: commit-time errors were discarded because `br.Close()` was deferred without checking its error. A
  deferred unique-constraint violation produced `n=2, err=nil`, zero rows stored (postgres#342, fixed in
  v0.14.4 by postgres#351). Still open: a primary-key-changing UPDATE leaves the old row (#386), and int8 max
  is stored as int8 min on amd64 (#402).

Signing and license. `postgres` has `publish.yml` with cosign keyless signing, SLSA L3 provenance and registry
registration (workflow present; not verified that it has run). `mysql` has none.

To certify:

- `postgres` destination (S to M): bump the built-in to v0.14.4 or later on `main` (#342); fix #343, #386 and
  #402; acceptance test with a `ReadN`-to-`Read` adapter;
  destination kill -9 chaos test (the repo's `test/chaos` covers the source); benchi config; delivery-semantics docs.
- `mysql` destination (M): merge #193; SIGKILL mid-transaction test; benchi config; docs; signed publish;
  decide on auto-create and evolve; handle key-changing updates.

## 3. Elasticsearch (`ConduitIO/conduit-connector-elasticsearch`)

CI was red because the pinned `elasticsearch:7.17.3` and 8.2.0 containers crash on cgroup v2 runners (JVM
NullPointerException), the Makefile never ran the unit tests (make expanded `$(go list ...)` before the shell), and a
stale unit test expected the wrong type. elasticsearch#152 fixes all three; CI is green on it (test,
golangci-lint, validate-generated-files).

Acceptance. It passes, weakly: source acceptance tests all skip (`NewSource` is nil), and
`ReadFromDestination` returns its input, so the write test reads nothing back (#156).

Parity with the Kafka Connect Elasticsearch sink:

| Option | Status |
| --- | --- |
| `connection.url` | Supported: `host`, single address only |
| Username/password, API key, Cloud ID, service token | Supported (API key README lists v6 to 8 only) |
| SSL trust | Approximated: certificate fingerprint only; no CA cert, no skip-verify |
| Index per topic, `topic.index.map` | Approximated: `index` is a Go template, default `opencdc.collection` |
| `key.ignore` | Approximated: empty key falls back to `create` with an auto ID (not idempotent on retry) |
| `schema.ignore` | Missing: ES dynamic mapping, no mapping management |
| `write.method` | Approximated: key present means `update` with `doc_as_upsert` (a merge, so removed fields persist); key absent means `create` |
| `behavior.on.null.values` | Approximated: delete record deletes by key; nil `Payload.After` on create/update likely panics (not run) |
| `behavior.on.malformed.documents`, `drop.invalid.message` | Missing: any item error fails the batch |
| `batch.size`, `linger.ms` | Approximated by SDK batch settings; connector `bulkSize` is a no-op |
| `max.retries`, `retry.backoff.ms` | Missing: `retries` is a no-op, README documents the wrong default (#155) |
| Timeouts, `max.in.flight.requests`, `data.stream.*` | Missing |
| `type.name` | Supported (v5/v6) |

Beyond Kafka Connect: a source (v8 only) and ES 5 through 8.

Delivery semantics (reading the code; no failing tests written yet):

- #153: `destination/destination.go:135,143` return `n+1` when item `n` fails, so the SDK acks the failed
  record. Only the last record of a batch is protected. Invariants 1 and 3. Treat as sev-0 for this connector.
- #154: status 404 is treated as success for every operation, so with auto-create off a missing index drops
  records.
- #155: the response item count is never checked against the request; an item without an action key is
  skipped with a warning; no retry or backoff on 429/5xx.
- Keyed writes are idempotent on retry; keyless writes duplicate on redelivery.
- Source (#157): `search_after` on `_seq_no` alone; `_seq_no` is per shard, so multi-shard indexes can skip
  documents. A failing worker exits silently and `Read` blocks. Updates and deletes are never emitted.

Schema handling. No mapping management. Structured payloads are marshalled to JSON; raw payloads are trusted
to be valid JSON, otherwise ES returns a per-item error that hits #153. Because updates merge, a CDC update
that removes a field leaves the old field in ES.

OpenSearch. Not tested. The v7 (7.14 and later) and v8 clients check the server product header, which
OpenSearch does not send, so they are likely rejected. The v5/v6 clients skip the check but use legacy `_type`
paths. No OpenSearch connector exists in `ConduitIO` or `conduitio-labs`. An OpenSearch mode needs the
`opensearch-go` client or a raw HTTP bulk client, an OpenSearch integration suite, and the same bulk-response
fixes.

Tests. Unit tests, a mocked destination test, four integration suites (ES 5.6.16, 6.8.23, 7.17.29, 8.19.3) in
CI. No chaos, benchi, fuzz or partial-failure bulk test.

Signing and license. Apache-2.0; headers still read "Meroxa, Inc. and Miquido". No signing: GoReleaser

Delivery semantics. Source: auto-commit off; offsets committed only for acked records, after 1000 acks or 5s
and on close, so `kill -9` gives at-least-once with up to 1000 records or 5s of duplicates. Invariant 1 holds.
Resume uses the consumer group, not the stored position offset; if the group is lost or changed, the reset
policy applies and `AtEnd` can skip records (a docs and config risk). `OnPartitionsRevoked` is a TODO, so
rebalances may give duplicates. The fetch-error path (`FranzConsumer.Consume`, the `fetches.Err()` branch with
`retryGroupJoinErrors`, which matches a typed `*kgo.ErrGroupSession` or an error whose text contains "unable to join
group session") was suspected of dropping records and is resolved as not a loss: franz-go invalidates the
consumer cursors on group-session loss and re-fetches from the committed offsets (franz-go `consumer_group.go`
around lines 422, 442, 685 and 1607), and a fencing probe confirmed it. The probe ran on Redpanda only; the cursor
reset is read from franz-go source for Kafka, not observed. Records from that poll are
redelivered, so the effect is duplicates, not loss. A follow-up that delivers those records instead of discarding
them was `ConduitIO/conduit-connector-kafka#314`, closed unmerged on 2026-10-13; it was not a loss fix.
Destination single-record path is correct. Destination batch path (#308, fixed): results were appended from
concurrent callbacks without a lock, and the returned index was a completion-order index, so a failed record that
completed last was acked. Fixed by #312 (merged 2026-10-13, released in v0.12.6 and v0.13.0).

(workflow and green runs seen; signatures not verified on artifacts).

The README describes a `bufferSize` parameter that does not exist.

Delivery semantics. Destination: `Write` calls `PutObject` synchronously and returns after success, so acks
follow durable storage (invariant 1 holds). No internal buffer; un-acked batches are retried under new keys, so
duplicates, not loss. Source (#1029, fixed in v0.9.5 by s3#1037): CDC used strict `LastModified.After`
at one-second resolution and the position stored only seconds, so objects landing in the watermark second were
missed; objects created during the snapshot below the snapshot maximum were missed; long multipart uploads were
missed; `ListObjectVersions` pagination passed `KeyMarker` without `VersionIdMarker`. These were invariant
2 and 3 violations. The v0.9.5 release notes describe the new watermark (a lookback window over the store's own
timestamps). Whole objects are read into memory with no size cap. Updates and deletes need bucket
versioning.

Schema handling. None. Structured payloads become JSON text in a string column; `Payload.Before` is dropped
(`format/json.go:40`, `format/parquet.go:48`), so update and delete records lose their before image. That is a
format limitation (typed output is s3#1034). The defect behind #1030 was a panic on delete records with no `After`
payload; the fix is s3#1038.
No schema derivation, drift handling, nested types or unions.

Signing and license. Apache-2.0. The latest release is v0.9.5 (2026-10-14); v0.9.4 (2026-10-08) shipped cosign
keyless bundles and SLSA L3 provenance and is registered (registry PR #36); the inventory's "not in the registry
index" is stale. Whether v0.9.5 carries the same signing was not checked.

Credentials (s3#1021) and endpoint (s3#1022). See the next section. The endpoint warning fix is s3#1028.

## s3#1021 credential chain: security review, design in review

The first implementation (s3#1027) made static keys optional and fell back to the AWS default credential chain.
An automated security review found two problems, and the PR is a draft on hold:

1. Confused deputy. With the default chain any pipeline author inherits the Conduit host's ambient AWS identity
   (EC2/ECS/EKS role, environment, `~/.aws`). Conduit's API is unauthenticated by default, so anyone who can
   create a pipeline can read and write every bucket the host role can reach.
2. Exfiltration and SSRF. Combined with a user-supplied `aws.endpoint` (s3#994), the connector sends
   SigV4-signed requests made with host credentials to an attacker-controlled endpoint.

Decision 1 (approved 2026-10-12) is an engine-provided operator setting for built-in connectors. The design is
draft PR `ConduitIO/conduit#3041` (Tier 1, security); s3#1027 stays on hold until it is signed off. Properties
settled in that design after fresh-context review:

- Ambient credentials are off by default and are an operator decision, not a pipeline-author one.
- Under ambient credentials a user-set `aws.endpoint` is refused unless it is in the operator's
  `allow-endpoints`; otherwise only the SDK's own endpoint resolution is used. Matching AWS-owned domain
  suffixes is not sufficient, because tenants control hosts under them (API Gateway, load balancers).
- https only; link-local and instance-metadata addresses are refused; redirects to hosts that are not permitted
  never carry credentials.
- `enabled=true` requires a non-empty `allow-resources` (exact bucket names, no wildcards) or an explicit
  `allow-any-resource: true`. Ambient credentials are refused when a proxy environment variable is set, unless the
  operator sets `allow-proxy`, because a proxy bypasses the dial-time link-local guard.
- The protection is cooperative: it constrains built-in connectors that use the policy. It is not a sandbox.
- Standalone plugins are out of scope for v0.21. The registry `s3` therefore cannot use the ambient chain until a
  later change, and a pipeline must name `builtin:s3` when a registry `s3` is installed, because the standalone
  plugin takes precedence.

A separate hardening change restricts what standalone plugin processes receive from the engine; see the draft
design doc, `ConduitIO/conduit#3043`.
