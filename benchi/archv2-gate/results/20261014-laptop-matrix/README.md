# Engine matrix, 2026-10-14, laptop

> **Superseded by `../20261015-aws-matrix/`.** That run, on a dedicated VM with 60 s windows and A/A
> floors of a few percent, finds the prototype resolved _slower_ than v1 and v2 in most 1x1 sessions.
> This laptop run's floors hid that. Read the AWS run first; this file is kept as the record.

**Indicative laptop numbers, not a gate result and not a performance claim.** The machine was shared and
heavily loaded, the windows are shorter than the gate requires, and no number here may be quoted outside
this directory as a measurement of Conduit. They are an input to the single-engine design (#2971), to be
replaced by the quiesced-hardware run.

The 13 sessions of `../../matrix/run.sh`: v1, arch-v2 (`v2`) and the staged-batch prototype
(`proto`, #2978), across pipeline shape (1x1, 2x2, 4x4), ack delivery (unbuffered, buffered) and destination
batching, plus one session for "Alternative A" (arch-v2 with the source batch at 100). Every arm ran twice
per round, so each carries its own A/A floor taken in the same session. `matrix.md` has every arm and
comparison with per-round deltas; it is generated by `archv2-gate -rerender .` and so is each
`summary.md`. This file is the written read of it.

## Setup

- Apple M3 Max, 16 cores, 64 GB; Docker Desktop 29.6.2 (16 CPUs, 7.7 GB for the VM).
- **Not quiesced.** Other work ran throughout. The host's 1-minute load average ranged from about 6 to
  about 290 during the sessions (`host_load` in each `runs.csv`); the three buffered destination-batching
  sessions ran at about 200 or above throughout. Load does not map simply onto the floors: those three
  have some of the narrowest, and the widest (±262%) is in a session whose load swung from 12 to 266. A
  swing during a session seems to hurt more than a steady high load, but this run cannot separate the two.
- 5 rounds per session, 8 s warmup discarded, **25 s window** (the gate requires 60 s). Run between
  18:24Z and 22:47Z, sessions in the order of `run.sh`.
- Binaries in `BUILDS.txt` (name, commit, SHA-256; the SHA-256 of each arm is also in its session's
  `env.json`). `v1` and `v2` are one binary built from `c60003bb`, the prototype's merge base; `proto` is
  #2978 at `0c92b617`. All three carry `../../matrix/patches/bench-ack-latency.patch`, inert unless the
  buffered knob is set. `conduit-main` was built for `drift.sh`, which was not run.
- Generator sources and `builtin:file` sinks; records counted at the sink.

## What this says

- **The prototype never came out slower.** In no session is `proto` resolved, or suggestive, below `v1` or
  `v2`. Its worst median against v1 is -8.5% (1x1 buffered), inside a ±27% floor.
- **With destination batching, the prototype is ahead of v1** in five of six sessions, resolved: +13% at
  1x1 with buffered acks, about +106% to +118% at 2x2 and about +196% to +210% at 4x4. The 1x1 unbuffered
  session is suggestive (+37%, inside a ±47% floor). The lead grows with fan-in and fan-out.
- **Arch-v2 as built at the merge base stalls on batching destinations**, at about 85 to 90 records/s in
  every shape. This is the behaviour #2987 now refuses on `main` (arch-v2 rejects `sdk.batch.size` above
  1). It is why v1 and v2 were built from the merge base: the arm runs instead of being skipped. The
  prototype does not have the problem.
- **At 4x4 without destination batching**, both v2 and the prototype are resolved ahead of v1 (+85% and
  +112% unbuffered; the prototype +107% buffered). The prototype is not resolved ahead of v2 there.
- **Alternative A at 1x1** (source batch 100 on arch-v2) is resolved ahead of both v2 and the prototype on
  their default configurations. It is a configuration change as well as an engine one: the prototype was
  not run with the larger source batch, so this does not compare the two engines at equal settings.

## What this does not say

- **Nothing at 1x1 and 2x2 without destination batching is resolved.** Whether the prototype matches v1
  on the simplest pipelines, which is the bar for replacing it, is open. The medians lean that way at 2x2
  and are flat at 1x1, on floors of ±18% to ±262%.
- Prototype against arch-v2 without destination batching is never resolved, so this run does not show the
  staged engine beats the engine it replaces behind the flag in the default configuration.
- No session ran a real gRPC connector. Buffered acks model how a gRPC destination delivers acks; they are
  not one.
- `v1` and `v2` are the merge base, not current `main`. `drift.sh` (v1 and v2 from both commits in one
  session) was not run, so how much `main` has moved is unmeasured.
- 25 s windows on a loaded laptop. Floors this wide hide effects; a tie here is not evidence of no
  difference, and every resolved delta is a laptop delta, not a size to quote.
- Rates are not comparable across rows or with the 2026-10-08 sessions: v1 at 1x1 is 53126 in one session
  and 32422 in another, on the same binary.

The decision in #2971 rests on the quiesced-hardware run (`../../aws`), not on this directory.
